Revised 2026-11-05 for the Lucento Shared model (full transaction collaboration, wallet classification,
Owner/Partner terminology). Reassessed from scratch against the revised requirements — the phase structure
survives, but Phase 0's spike changes (the ignore-duplicates mechanism is gone), Phase 1 grows the wallet
column, and Phase 2's push path is simpler than originally planned while its test matrix is larger.

Phases are small, independently testable, and leave `main` shippable; server changes land before the builds
that need them (project rollout convention). **No phase starts before explicit product-owner authorization.**

Coordination note (2026-11-05): bank-asset and theme work is in flight on `feature/owner-round-10` with
uncommitted changes to `SyncRepository.kt`, `PulledRowRules.kt`, `WalletRepository.kt`, `RecurringRepository.kt`,

`SyncModels` edits and everything from Phase 2 on should wait until that work is committed, and Lucento Shared
work belongs on its own feature branch (ideally a separate worktree).

## Phase 0 — Server foundation (no app changes)

**Deliverable:** one additive migration on `lucento-test`; nothing user-visible.

- `supabase/migrations/<ts>_shared_space.sql`: `space_members` (one row per member, PK
  `(owner_id, partner_id)` — structurally multi-Partner), `space_invites`, `lucento_is_member_of()`,
  `lucento_max_partners()` (hardcoded 1 — the single limit home and future entitlement hook),
  `create_space_invite()`, `accept_space_invite()` (capacity check under an advisory lock), transactions
  attribution columns + actor-stamp trigger, wallets `classification` column + CHECK, widened select policies
  (all seven tables), widened transactions insert/update policies, grants/revokes. Details:
  ARCHITECTURE_PROPOSAL.md §2.1/§3.
- Verify with the rolled-back-transaction method: the full PERMISSION_MATRIX.md §4 checklist (now including
  Partner update/soft-delete, stale-skip under the Partner's uid, attribution immutability on edit,
  classification writes, and the capacity mechanics — refusal at limit, concurrent-accept serialization, slot
  freed on removal, and the two-member structural proof with `lucento_max_partners` locally returning 2),
  plus Owner regression, plus security/performance advisors.
- **Spikes (validate the mechanisms this design leans on):**
  1. As a Partner JWT, a bulk upsert of transactions containing one stale row → the stale row is skipped by
     `lucento_reject_stale_update` with no error, fresh rows return `{id, revision}` (batch-safety under the
     widened update policy).
  2. As a Partner JWT, a bulk upsert containing one non-transaction row → fails as expected (documents why the
     client-side table filter is a correctness requirement, and what error code the client will see).
  3. `softDelete` path (UPDATE setting `deleted_at`) as Partner → accepted; stale variant → skipped.

Dependencies: none. Risk: low-moderate (additive, but this is the security-critical change — an independent
`lucento-architect` review of the migration is recommended before it is applied anywhere).

## Phase 2 — Environment binding + Partner sync mode (the core)

- `SyncPreferences`: `environmentId`, `role` (`OWNER`/`PARTNER`); cleared wherever `syncedUserId` is cleared.
- `SyncRepository.sync()`: membership resolution at cycle start; envId substituted at the single `userId` seam;
  `MembershipRevoked` result.
- Partner cycle: pushes `transactions` and transaction tombstones only (hard filter — a correctness
  requirement, see ARCHITECTURE_PROPOSAL.md §3.6); normal upsert path, no special push variant.
- `SharedSpaceRepository` + `AppContainer` wiring (membership/invite state Flow, the six actions); membership
  state modeled as a **list of members keyed by uid** (size ≤ 1 this release) so attribution label lookup and a
  future limit increase need no state-model rework.
- Repository-level role guards on structure-management mutations (wallet/category/budget/goal/recurring/debt
  repositories); transaction paths ungated.
- Recurring auto-posting + reminders gated to the Owner's device.

**Testing (JVM, the bulk of the matrix):** two engines (one per simulated user) against the taught
`FakeSyncServer`, covering ARCHITECTURE_PROPOSAL.md §5 scenarios 4–9 at engine level plus: lost-reply retry of
a Partner edit; concurrent Owner/Partner edits both orders; Partner edit vs Owner delete and the reverse;
double delete; a stray non-transaction dirty row on a Partner device (stays dirty, surfaced, batch unharmed);
revocation mid-cycle; seed folding on join; transfer legs and per-currency totals identical on both sides after
convergence; budget fold unaffected.

Dependencies: Phases 0–1, and the round-10 sync changes committed first. Risk: highest of the project —
mitigated by the seam being mechanical and the engine itself not changing.

## Phase 3 — Join / leave / removal flows

- Join: invitation check at the `probeAccount` call sites; acceptance screen; wipe (existing
  `LocalLedgerReset`) → bind environment → pull-first bootstrap (existing restore path with envId);
  resume-on-reopen.
- Leave / removed: membership deletion; `MembershipRevoked` notice; wipe + return to own-account probe/restore;
  unsynced-changes confirmations reuse the `AccountBoundary` wording and ordering guarantees (durable marker
  first).

**Testing:** JVM state-machine tests (join with/without unsynced data, kill-during-join resume, removed while
offline, leave with pending rows); wipe tests mirror the existing sign-out tests.

## Phase 4 — UI

- `feature/sharedspace` screen (four states, UX_FLOW.md §1–3, §5), SettingsHub row, Home invitation card,
  removal notice.
- Role gating on existing screens: structure-management editors and entry points hidden for the Partner;
  the full transaction surface (composer, editor, delete) stays for both.
- Attribution display (detail rows + optional history chip, Shared-Space-only; labels with email fallback).
- Wallet classification: one field in the wallet editor (Owner, Shared-Space-only), label on wallet
  card/detail, optional grouping in the Wallets list; absent for solo users.
- Overridden-change notice copy variant naming the other person (copy-only).
- Validation per standing design rules: both themes, font scaling, small/large screens, TalkBack,
  empty/loading/error states; `ScreenshotTourTest` extended with the states reachable without a second account.

## Phase 5 — Hardening, docs, release

- Two-device end-to-end on `lucento-test` (two real test accounts) mirroring docs/SYNC.md "First end-to-end
  test", extended with: cross-editing and cross-deleting each other's transactions, concurrent edits, removal
  while the Partner is offline, device change in both roles, classification round-trip.
- Forged-API checks with a Partner JWT (PERMISSION_MATRIX.md §4) against the live test project.
- Docs: docs/SYNC.md gains a Lucento Shared section (membership resolution, Partner push filter, rollout
  order, revocation semantics); README/ROADMAP; docs/handover updated.
- Production migration applied only on owner approval; release rollout after it.

## Cross-cutting requirements

- Every phase: `./gradlew testDebugUnitTest assembleDebug` green before push; no claimed result without seeing
  it pass. Feature branches per phase; no commits/merges without authorization.
- No new third-party dependencies anticipated (supabase-kt postgrest covers RPCs and table ops).
- Financial invariants re-asserted wherever Lucento Shared touches a flow: Long minor units, per-currency
  totals, atomic transfer legs, idempotency keys, budget = sum of category allocations.

## Out-of-scope guardrails (stop and surface if a phase appears to need one)

Billing/entitlements; a second Partner; relationship categories; environment switching or ownership transfer;
email delivery; wallet-level access control; approval workflows; any change to conflict resolution or a new
sync architecture; any website work (and no use of "Companion" anywhere — reserved for a future web product).
