# Optional cloud sync (Supabase + Google Sign-In)

Lucento stays local-first. Room is the source of truth for every read and write, every core feature works offline
with no account, and nothing leaves the device until the user signs in with Google **and** keeps cloud sync on in
Settings → Cloud sync. Signing out never deletes local data.

## Architecture

```
UI (Settings → Cloud sync) ──► SettingsViewModel ──► AuthRepository ──► Credential Manager (Google ID token)
                                     │                    └──────────► Supabase Auth (signInWith IDToken)
                                     ├─► SyncScheduler ──► WorkManager ──► SyncWorker ─┐
                                     └─► SyncRepository.sync() ◄───────────────────────┘
                                              │ push dirty rows + tombstones   │ pull changed rows
                                              ▼                                ▼
                                     Room (dirty / synced_at / sync_tombstones) ⇄ Supabase Postgres (RLS)
```

| Piece | File |
|---|---|
| Client factory (null when unconfigured) | `data/sync/SupabaseModule.kt` |
| Google Sign-In → Supabase session | `data/sync/AuthRepository.kt` |
| Push / pull / merge engine | `data/sync/SyncRepository.kt` |
| Wire DTOs, conflict rule, results | `data/sync/SyncModels.kt` |
| Background runs | `data/sync/SyncWorker.kt` (`SyncWorker`, `SyncScheduler`) |
| Sync cursor / enabled flag / last error | `data/sync/SyncPreferences.kt` (DataStore `sync_preferences`) |
| Cloud schema + RLS | `supabase/migrations/*.sql` |
| Local schema (Room v6) | `Migrations.MIGRATION_5_6`, `SyncTombstoneEntity` |

## What syncs

| Room table | Cloud table | Notes |
|---|---|---|
| `wallets` | `public.wallets` | |
| `categories` | `public.categories` | gained `updated_at` in v6 (backfilled from `created_at`) |
| `transactions` | `public.transactions` | transfer legs keep their `client_uuid` + `-out`/`-in` suffix and `transfer_group` |
| `budgets` | `public.budgets` | |
| `goals` | `public.goals` | `photo_path` is **never** synced (a local file path); `scene_key` is |
| `goal_contributions` | `public.goal_contributions` | append/delete-only |

Not synced yet: **recurring schedules** (`recurring`), DataStore preferences (theme, currency, enabled modules,
display name), goal photos. See "Known limitations".

Amounts stay `bigint` minor units with their ISO 4217 code — no conversion, no floating point. `occurred_on` and
`target_date` stay epoch days. Only `created_at` / `updated_at` / `deleted_at` become `timestamptz`.

## Identity

Every synced row's cloud primary key is its local `client_uuid` (text, so transfer-leg suffixes are valid). Room's
autoincrement `id` never leaves the device; foreign keys are translated to the parent's `client_uuid` on push and
back to local ids on pull. v6 gave `wallets`, `categories`, `budgets` and `goals` a `client_uuid` (backfilled for
existing rows, generated by each repository's create path from then on). Because ids are stable and every push is
an upsert on `id`, retrying a push can never create a duplicate.

## Change tracking (no repository had to change its delete or edit path)

- `dirty` (default 1): set for new rows by default, and set again by an `AFTER UPDATE` trigger whenever `updated_at`
  changes **and** `synced_at` does not. Ordinary repository edits bump `updated_at` and leave `synced_at` alone, so
  they are marked; the sync engine's own pull writes set a fresh `synced_at` in the same statement, so they are not.
- After a successful push, `clearDirtyIfUnchanged(client_uuid, updated_at_at_read_time)` clears the flag only if
  the row was not edited again during the push — a concurrent edit stays dirty and goes out next cycle.
- Deletions: an `AFTER DELETE` trigger on every synced table writes `(table, client_uuid, deleted_at)` to
  `sync_tombstones`, including rows removed by `ON DELETE CASCADE`. Tombstones are pushed as remote soft deletes
  (`deleted_at = now`), never hard deletes, so a slower device sees the row disappear instead of resurrecting it.
  Pushed tombstones are pruned after 30 days.

## Sync cycle (`SyncRepository.sync`)

1. Require a configured client and an authenticated Supabase user, else `NotConfigured` / `NotSignedIn`.
2. Push tombstones, children before parents (contributions → transactions → budgets → goals → categories → wallets).
3. Push dirty rows, parents before children (wallets → categories → budgets → transactions → goals → contributions).
   A child whose parent has no `client_uuid` yet waits for a later cycle instead of pushing an orphan.
4. Pull rows with `updated_at >= cursor` in the same parent-first order and merge them (below).
5. Store the new cursor (`start time − 5 s` overlap; re-pulled rows are idempotent) and clear the last error.

Any exception aborts the cycle with `Retryable`; the cursor does not advance, nothing local is deleted, and unpushed
rows stay dirty. `SyncWorker` retries with WorkManager backoff (up to 5 attempts per run).

## Conflict resolution

Last-write-wins per row by `updated_at`, enforced twice:

- **On pull** (client): remote newer than local → apply remote. Local newer **and dirty** → keep local; it is pushed
  next cycle. Remote tombstone vs local edit: the delete is skipped if the local row is dirty with an `updated_at`
  newer than `deleted_at` (`localWinsOverRemoteDelete`, unit-tested); ties go to the delete.
- **On push** (server): a `BEFORE UPDATE` trigger (`lucento_reject_stale_update`) silently skips any update whose
  `updated_at` is older than the stored row's, and rejects any change of `user_id`. Equal timestamps pass, so a
  retried push is idempotent. Pushed rows always send `deleted_at: null`, so a local edit newer than a remote
  delete brings the row back everywhere; tombstone pushes set both `deleted_at` and `updated_at` so other devices
  (which pull by `updated_at`) receive them.

Concurrent edits to the same row on two offline devices therefore resolve to the later edit by wall clock; the
earlier one is overwritten on the other device once both have synced. Edits to different rows never conflict.

## First sign-in

Linking an account never assumes either side is empty and never replaces local data with a cloud response:

- Every existing local row starts `dirty`, so the first cycle uploads full history (upsert — safe to interrupt and
  repeat).
- The first pull uses cursor 0 and merges whatever the account already has by the rules above; an empty cloud
  response changes nothing locally.
- Direction: push first, then pull. A second device signing into the same account uploads its own rows and receives
  the first device's, so both devices end up with the union. **Duplicates by meaning are possible**: if two devices
  each created a wallet named "Cash" before ever syncing, the account will have two "Cash" wallets (different ids).
  Nothing is merged by name.

## Security

- Table privileges: `select/insert/update/delete` granted to `authenticated` only; `anon` has none.
- RLS is enabled on all six tables. Each has `select`/`insert`/`update`/`delete` policies of
  `auth.uid() = user_id`; insert and update also use `with check (auth.uid() = user_id)`, so a row cannot be created
  for, or moved to, another account. The client always filters by `user_id` too, but that is not the boundary.
- Composite foreign keys `(user_id, parent_id)` stop a row from referencing another user's parent.
- Supabase's security advisor reports no findings with all four migrations applied.
- Verified against the live project as the real `authenticated` and `anon` roles, inside one transaction that was
  rolled back (two throwaway `auth.users` rows; nothing persisted): user A can write its own row and cannot write a
  row owned by B or move its row to B; B sees, updates and deletes 0 of A's rows and cannot upsert onto A's id;
  signed-out reads are denied; a stale upsert is skipped and a newer one applied. This check also caught a missing
  table grant (fixed by migration 4) that would have made every sync request fail.
- The APK contains only the Supabase URL and the **publishable** key. No service-role key, database password or
  Google client secret exists anywhere in the repository or the app. Values come from `local.properties` / CI env
  (see `local.properties.example`) and are never committed.
- Network: HTTPS only (`res/xml/network_security_config.xml`). No tokens, emails or financial values are logged.
- Session storage and refresh are handled by supabase-kt's Auth plugin.

## Setup required

Done already: the Supabase project `lucento` (`hmtcuttadbgbldvzsfhz`) has all four migrations in
`supabase/migrations/` applied, with RLS enabled and verified.

Still needed before anyone can sign in:

1. **Google Cloud Console** → APIs & Services → Credentials:
   - Create an OAuth client of type **Web application**. Copy its client ID (and keep its secret for step 2 only).
   - Create an OAuth client of type **Android** for package `com.lucento.app` with the release signing SHA-1, and one
     for `com.lucento.app.debug` with the debug keystore SHA-1 (`./gradlew signingReport`).
   - Configure the OAuth consent screen (app name, support email, scopes `email`, `profile`, `openid`).
2. **Supabase dashboard** → Authentication → Sign In / Providers → Google: enable it and paste the **Web** client ID
   and secret. Add the Web client ID to "Authorized Client IDs" if that field is shown.
3. **Local build**: in `local.properties` set `LUCENTO_GOOGLE_WEB_CLIENT_ID` (the Web client ID — not the Android
   one), plus `LUCENTO_SUPABASE_URL` and `LUCENTO_SUPABASE_ANON_KEY`. For CI, add the same three names as repository
   secrets and expose them as env vars to the Gradle steps.
4. Sign in on a real device or a Google Play emulator image and run "Sync now".

Until steps 1–3 are done the Settings section says setup is incomplete and offers no sign-in button.

## Known limitations

- Conflict ordering trusts device clocks. A device with a badly wrong clock can win or lose conflicts it shouldn't.
- Pull pages are capped at 1000 rows per table per cycle; a larger backlog arrives over several cycles.
- Recurring schedules, preferences and goal photos are not synced.
- Rows with identical meaning created separately on two devices before their first sync are not de-duplicated.
- End-to-end sign-in and a real push/pull against Supabase have not been exercised yet (blocked on the Google OAuth
  setup above). RLS was verified with simulated JWT claims at the SQL level, not yet through the app with two real
  Google accounts.
- Applying a remote delete locally writes a local tombstone that is pushed once more (harmless: the row is already
  deleted remotely; it only bumps `updated_at`).
