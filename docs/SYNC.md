# Optional cloud sync (Supabase + Google Sign-In or email)

Lucento stays local-first. Room is the source of truth for every read and write, every core feature works offline
with no account, and nothing leaves the device until the user signs in with Google **and** keeps cloud sync on in
Settings → Cloud sync. Signing out removes that account’s data from this phone and clears the sync
binding, so the next account starts clean and one person’s ledger is never uploaded into another account.

## Architecture

```
UI (Settings → Cloud sync) ──► SettingsViewModel ──► AuthRepository ──► Credential Manager (Google ID token)
                                     │                    └──────────► Supabase Auth (signInWith IDToken)
                                     ├─► SyncScheduler ──► WorkManager ──► SyncWorker ─┐
                                     └─► SyncRepository.sync() ◄───────────────────────┘
                                              │ push dirty rows + tombstones   │ pull changed rows
                                              ▼                                ▼
                                     Room (dirty / synced_at / sync_tombstones) ⇄ Supabase Postgres (RLS)
```

| Piece | File |
|---|---|
| Client factory (null when unconfigured) | `data/sync/SupabaseModule.kt` |
| Google Sign-In or email + password → Supabase session | `data/sync/AuthRepository.kt` (UI: `feature/settings/ConnectAccount.kt`, onboarding's sync step, Settings › Cloud sync) |
| Push / pull / merge engine | `data/sync/SyncRepository.kt` |
| Wire DTOs, conflict rule, results | `data/sync/SyncModels.kt` |
| Background runs | `data/sync/SyncWorker.kt` (`SyncWorker`, `SyncScheduler`) |
| Server I/O (fakeable in tests) | `data/sync/SyncRemote.kt` (`SupabaseSyncRemote`) |
| Sync cursor / account / enabled flag / last error | `data/sync/SyncPreferences.kt` (DataStore `sync_preferences`) |
| Cloud schema + RLS | `supabase/migrations/*.sql` |
| Local schema (Room v6) | `Migrations.MIGRATION_5_6`, `SyncTombstoneEntity` |

## What syncs

| Room table | Cloud table | Notes |
|---|---|---|
| `wallets` | `public.wallets` | |
| `categories` | `public.categories` | gained `updated_at` in v6 (backfilled from `created_at`) |
| `transactions` | `public.transactions` | transfer legs keep their `client_uuid` + `-out`/`-in` suffix and `transfer_group` |
| `budgets` | `public.budgets` | |
| `goals` | `public.goals` | `photo_path` is **never** synced (a local file path); `scene_key` is |
| `goal_contributions` | `public.goal_contributions` | append/delete-only |
| `recurring` | `public.recurring` | v9: `client_uuid`, `dirty`, `synced_at`, `base_revision` + triggers (MIGRATION_8_9); debt payments carry `to_wallet_id`, `interest_minor` |
| `debt_terms` | columns of `public.wallets` | v9: `interest_rate_bps`, `repayment`, `term_months`, `installment_minor`, sent with the wallet (a terms edit bumps the wallet's `updated_at`); pre-v9 builds never send them, so the server keeps them |

Not synced: DataStore preferences (theme, currency, enabled modules, display name) and goal photos. See "Known
limitations".

A recurring occurrence's idempotency key uses the schedule's `client_uuid` (`recurring-<uuid>-on-<day>`), so marking the
same payment paid on two devices records it once. Server schema: `supabase/migrations/20261026120000_recurring_and_debt_terms_sync.sql`
(**must be applied before a v9 build syncs**: until then the extra wallet columns and the `recurring` table are unknown
to the server and every sync fails safely, keeping all local data and dirty flags).

### Accounts

- **Google** (native, Credential Manager → ID token → `signInWith(IDToken)`), or **email + password** (`signUpWith(Email)` /
  `signInWith(Email)`; at least 8 characters).
- With "Confirm email" on (the project default), a new email account has no session until the user opens the link;
  the app says so and the user signs in afterwards.
- Onboarding asks once (after currency and look): connect Google or an email account, or "Not now". Connecting turns
  sync on, but the **first sync runs only when onboarding finishes**, so an existing account's data is never merged
  with categories the user hasn't confirmed yet.

Amounts stay `bigint` minor units with their ISO 4217 code — no conversion, no floating point. `occurred_on` and
`target_date` stay epoch days. Only `created_at` / `updated_at` / `deleted_at` become `timestamptz`.

## Identity

Every synced row's cloud primary key is its local `client_uuid` (text, so transfer-leg suffixes are valid). Room's
autoincrement `id` never leaves the device; foreign keys are translated to the parent's `client_uuid` on push and
back to local ids on pull. v6 gave `wallets`, `categories`, `budgets` and `goals` a `client_uuid` (backfilled for
existing rows, generated by each repository's create path from then on). Because ids are stable and every push is
an upsert on `id`, retrying a push can never create a duplicate.

## Change tracking (no repository had to change its delete or edit path)

- `dirty` (default 1): set for new rows by default, and set again by an `AFTER UPDATE` trigger whenever `updated_at`
  changes **and** `synced_at` does not. Ordinary repository edits bump `updated_at` and leave `synced_at` alone, so
  they are marked; the sync engine's own pull writes set a fresh `synced_at` in the same statement, so they are not.
- `base_revision` (v7): the server `revision` the local row was last synced at. Repository edits carry it forward
  unchanged (`copy()`), so an edit records which version it was made from.
- After a push the server accepted, `markPushed` records the returned revision as the new base and clears `dirty`
  only if the row wasn't edited again during the push (that edit stays dirty and goes out next as a causal successor).
- Deletions: an `AFTER DELETE` trigger on every synced table writes `(table, client_uuid, deleted_at, base_revision)`
  to `sync_tombstones`, including rows removed by `ON DELETE CASCADE`. Tombstones are pushed as remote soft deletes,
  never hard deletes, so a slower device sees the row disappear instead of resurrecting it. Pruned after 30 days.
- **Where the triggers come from.** Upgraded databases get them from `MIGRATION_5_6` / `MIGRATION_6_7`. A fresh
  install never runs a migration (Room builds tables from the entities), so `SyncTriggers.ensure` creates them on every
  open (`IF NOT EXISTS`). Before that fix (not in commit `026c2f8`), a new install had no triggers: its deletions
  never propagated and edits after the first sync were never pushed. `MigrationTest.freshInstall_hasTheSyncTriggers`
  covers it and fails without the fix.

## Sync cycle (`SyncRepository.sync`)

1. Wait for the stored session to load (`awaitInitialization`), then require a configured client and a signed-in
   user, else `NotConfigured` / `NotSignedIn`.
2. **One account per device.** The first account to sync is recorded (`synced_user_id`). A different account is
   refused with `AccountMismatch` before anything is pushed or pulled: this device's rows already exist under the
   first account's ids, so pushing them elsewhere would fail RLS on every attempt and mix two people's records.
3. Give fresh-install seed categories (inserted by `CategorySeed`, which can't set v6 columns) a stable id:
   `seed-<user>-<kind>-<name>`, so the same seed on two devices of one account becomes one cloud row.
4. Push tombstones (children first), each with its `base_revision`. The server reports whether it accepted each.
5. Push dirty rows (parents first) with their `base_revision`; the server returns `{id, revision}` for each row it
   accepted. A row whose parent can't be referenced yet (no stable id) stays dirty for a later cycle.
6. Pull, parents first. For each table, rows whose push or delete the server **rejected** are fetched by id first and
   replaced by the server's copy (a rejected delete therefore brings the newer edit back). Then every row whose
   server-assigned `server_updated_at` is at or after the cursor is read in **keyset** pages of 500 —
   `(server_updated_at, id) > last seen` — so a row updated by another device mid-read moves to the end instead of
   shifting the next page and being skipped (which offset paging allowed). A row whose parent hasn't arrived is
   deferred only while a parent might still arrive in a later page. A wallet, category or goal that is already
   deleted is restored locally so the child can be stored (a missing category with no row left to restore becomes
   "Uncategorized"; a missing wallet becomes "Restored account", keeping the original id and the transaction's
   currency). The restored parent is not pushed, so other devices that deleted it stay deleted until they too
   receive the child. The cursor then moves. Remote deletions are applied after all upserts, children first; one the
   local schema still refuses (this device added a transaction to a wallet another device deleted) is kept and counted
   as a conflict, never fatal.
7. Save the new cursor: the newest `server_updated_at` seen minus 60 s (catches writes stamped before but committed
   after the read; re-pulled rows are idempotent), never past a deferred row. Then clear the last error.

Any exception aborts the cycle with `Retryable`; the cursor does not move, nothing local is deleted, and unpushed rows
stay dirty, so the next cycle repeats the work. `SyncWorker` retries with WorkManager backoff (up to 5 attempts).

"Sync now" and the 30-minute worker share one in-process lock (`SyncFlight`) and, on a device, one file lock under
the app's files directory. A second cycle waits; it does not run beside the first. The file lock is released by the
operating system if the process is killed, and the cursor moves only after a cycle finishes, so a killed cycle retries
without a stuck lock or a half-applied cursor. The manual worker is unique work with `KEEP` (a second tap does not
cancel the running one). The periodic worker has its own unique name; the lock is what keeps the two from overlapping.

## Clocks

- **Which rows are new** is decided by `server_updated_at`, set by the database on every insert and update
  (`lucento_stamp_server_time`). No device clock is involved, so a phone whose clock runs hours behind still has its
  changes pulled by everyone else.
- **Which edit wins** is decided causally first, by revisions — see below. Device edit time only breaks ties between
  edits that are genuinely concurrent, and the server clamps an edit time more than 5 minutes in the future to its own
  time **before** comparing, so a fast clock can't win a conflict it would lose with a correct one.

## Conflict resolution

Every server row has a `revision` (+1 on each accepted write); each local row remembers the revision it was based on.

- **Causal successor** — the edit's base equals the server's current revision, i.e. the user edited the latest version.
  It wins outright, whatever any clock says. (Time-only last-write-wins got this wrong: a device whose clock ran an hour
  slow could pull the newest version, edit it, and have that edit silently discarded as "older".)
- **Concurrent** — the server row changed since the edit's base (or the base is unknown). The strictly later edit time
  wins. A tie on the server still keeps the stored row. A **pending local edit** at that same timestamp is not
  overwritten by the pull: it is moved one millisecond later and pushed again in the same cycle, so the unsynced
  change is the one that remains. A clean local row (nothing waiting) still takes the server's copy on a tie.
- Server (`lucento_reject_stale_update`) and client (`localEditWins` / `pullDecision`) apply the same rule, so they
  always agree. A write the server refuses is not retried forever: the next pull fetches the server's copy by id and
  applies it, and the conflict is counted ("N changed on two devices at once — the later edit was kept").
- A clean local row (nothing unpushed) always takes the server's copy, even with an older edit time.
- Deletes follow the same rule: a delete based on the current revision applies even from a slow clock; a delete that
  lost to a newer concurrent edit is rejected and the edited row comes back on the deleting device. On the receiving
  side a remote delete is skipped only if this device holds a newer unpushed edit (`localWinsOverRemoteDelete`).
- Retries are idempotent: a push whose reply was lost is refused the second time (same edit, stale base) and resolved
  from the identical server copy — no duplicate, no lost edit.
- Why not server arrival order alone: it would let an edit made offline yesterday overwrite one made online today.
  Revisions keep offline editing correct without trusting arrival order or device clocks for sequential edits.

## First sign-in

Linking an account never assumes either side is empty and never replaces local data with a cloud response:

- Every existing local row starts `dirty`, so the first cycle uploads full history (upserts — safe to interrupt and
  repeat).
- The first pull starts from the beginning and merges whatever the account already has; an empty cloud changes
  nothing locally.
- Direction: push first, then pull, so a second device on the same account ends up with the union of both.
  **Duplicates by meaning are possible**: two devices that each created a wallet named "Cash" before ever syncing give
  the account two "Cash" wallets. Nothing is merged by name, except fresh-install seed categories (step 3 above).

## Restoring on a new phone

Onboarding's welcome screen offers **I already have an account** (only in builds with sync configured):

1. A reminder: changes made on the old phone since its last sync stay there, so sync it first (recommended).
2. Sign in (Google or email), which turns sync on.
3. One full `SyncRepository.sync()` on this still-empty phone: it pushes only the fresh-install income seeds (their
   deterministic ids merge with the account's) and pulls everything.
4. If the account brought back a wallet or a spending category (`RestorePlan.hasData`), onboarding completes with
   `UserPreferencesRepository.completeRestore`: main currency = the one most restored wallets use, every module on,
   the current theme, and **no guided setup**. Periodic sync is scheduled.
5. An empty account continues with the normal setup from its first question, still connected. A failed download
   changes nothing and offers Try again or Set up as new. A restore interrupted by the app closing resumes on reopen.

Main currency, theme and enabled modules are device preferences (DataStore), never synced.

## Sign-out and switching accounts

"Disconnect" asks first, then cancels background sync, turns sync off, clears the Supabase session, and **wipes**
the local ledger (wallets, categories, transactions, budgets, goals, contributions, schedules, debt terms, goal
photos) plus the sync binding (which account, the pull cursor, the last error). Income categories are seeded
again, as on a fresh install. Theme and other device preferences stay. Anything that had not synced is lost —
the confirmation says so.

Signing in to a **different** account does the same wipe before any push. If nothing is waiting to sync, it happens
immediately. If there are unsynced changes, Lucento asks first; cancelling signs out of the new account and leaves
the previous ledger in place. Sync refuses to push while the signed-in account and the stored binding disagree
(`AccountMismatch`), so a background cycle cannot upload the previous ledger during that question.

The device is no longer permanently tied to the first account. Signing back in to an account downloads it again.

## Security

- Table privileges: `select/insert/update/delete` granted to `authenticated` only; `anon` has none.
- RLS is enabled on all six tables, each with `select`/`insert`/`update`/`delete` policies of `auth.uid() = user_id`;
  insert and update also use `with check`, so a row can't be created for, or moved to, another account. The client
  filters by `user_id` too, but that is not the boundary.
- Composite foreign keys `(user_id, parent_id)` stop a row from referencing another user's parent.
- Verified against the live project as the real `authenticated` and `anon` roles, inside transactions that were
  rolled back (throwaway `auth.users` rows; nothing persisted): user A can't write a row owned by B or move its row to
  B; B sees, updates and deletes 0 of A's rows and can't upsert onto A's id; signed-out reads are denied; a stale
  upsert is skipped and a newer one applied. Migration 5 was validated the same way (see below).
- Google sign-in uses a one-time nonce (SHA-256 sent to Google, raw value to Supabase), Supabase's documented
  Android flow, so a captured ID token can't be replayed.
- The APK contains only the Supabase URL and the **publishable** key — no service-role key, database password or
  Google client secret exists in the repository or the app. Values come from `local.properties` / CI env.
- Network: HTTPS only (`res/xml/network_security_config.xml`). No tokens, emails or financial values are logged.
- Sessions: supabase-kt stores the session on the device (`SettingsSessionManager`), restores it at startup and
  refreshes it before expiry. If a refresh fails offline the session is kept; if it can no longer be refreshed the user
  appears signed out and sync stops until they connect again.

## Setup required

Database: all five migrations in `supabase/migrations/` are applied to project `lucento` (`hmtcuttadbgbldvzsfhz`);
each file is named after the version Supabase recorded, so `supabase db push` sees nothing outstanding. Migration 5
(`20261025145902_server_clock_sync_cursor.sql`, applied 2026-10-25) adds `server_updated_at`, `revision` and
`base_revision`, the server-time stamp trigger, and the causal conflict rule. It is additive — nothing was dropped and
no existing value rewritten — and builds from commit `026c2f8` keep working against it (they send no base, so their
writes follow the concurrent rule). After applying: the security advisor reports no findings, and on the live triggers
(inside a rolled-back transaction) a causal edit from a slow clock is accepted, a stale concurrent edit is skipped and
another user sees no rows. The performance advisor's notes (`auth.uid()` re-evaluated per row in the RLS policies,
unindexed composite foreign keys, the old `*_user_updated` indexes now unused) predate it and are follow-ups.

Google sign-in. Lucento uses **native** Google sign-in (Credential Manager → Google ID token → Supabase
`signInWith(IDToken)`), not a browser redirect: there is no login web page, deep link or OAuth callback in the app.
On 2026-10-25 the live project reported the Google provider as **enabled**.

| Web OAuth client **ID** ("Lucento Supabase Web Client") | Google Cloud; Supabase → Google → Client IDs; `local.properties` `LUCENTO_GOOGLE_WEB_CLIENT_ID` | Yes — it is the ID token's audience; not secret |
| Web OAuth client **secret** | Google Cloud; Supabase → Google → Client Secret | **Never** |
| Android OAuth client(s) | Google Cloud only (package + SHA-1); nothing to copy anywhere | No (Google matches the app's signature) |

| Supabase service-role key | Supabase only | **Never** |

1. **Google Cloud Console**, all in the **same** project ("Lucento"):
   - OAuth consent screen: app name, support email, scopes `openid`, `email`, `profile`. While publishing status is
     **Testing**, only listed **test users** can sign in — add every account you test with.
   - **Web application** client: the "Lucento Supabase Web Client" already created is the right one. Its redirect URI
     (the Supabase callback) is only used by browser OAuth and is harmless here.
   - **Android** client for `com.lucento.app.debug` with the debug keystore's SHA-1 — required: Google issues ID
     tokens only to an app whose package and signing certificate are registered in the same project. On the
     development machine used for this work the debug SHA-1 is
     `49:AF:14:81:8D:53:F5:DF:68:42:03:3E:3C:1E:2E:DA:AA:AB:8C:75` (each machine's debug keystore differs — check
     with `./gradlew signingReport`).
   - **Android** client for `com.lucento.app` with the **release** keystore's SHA-1, and another with the Play App
     Signing SHA-1 if the app is distributed through Google Play.
   - Authorized domains / branding only matter for the consent screen and browser OAuth; the Lucento website domain
     and Search Console verification are unrelated to this flow.
2. **Supabase dashboard** → Authentication → Sign In / Providers → **Google**: enabled; **Client IDs** contains the
   **Web** client ID (the Android client IDs are not needed there); Client Secret = the Web client's secret; leave
   "Skip nonce check" **off** (Lucento sends a nonce). No redirect URL allow-list entry is needed for native sign-in.
3. Recommended: Sign In / Providers → **Email**: turn the provider off; Lucento never uses it and the project currently
   allows open email sign-up. **Do not** turn off "Allow new users to sign up" — that would also block every new
   Google user (Supabase creates the account on a user's first Google sign-in).
4. **Local build**: `local.properties` → `LUCENTO_GOOGLE_WEB_CLIENT_ID=<Web client ID>` (the Web one, not Android).
   `LUCENTO_SUPABASE_URL` and `LUCENTO_SUPABASE_ANON_KEY` are already set on the development machine.
5. **CI** (optional — CI builds fine without them; Settings then says sync isn't available): repository secrets
   `LUCENTO_SUPABASE_URL`, `LUCENTO_SUPABASE_ANON_KEY`, `LUCENTO_GOOGLE_WEB_CLIENT_ID`, exposed as `env:` on the Gradle

6. Test on a real device or an emulator image **with Google Play** and a Google account added; the sign-in sheet
   can't appear without one.

Diagnosing setup: in **debug** builds a failed sign-in appends a short diagnostic to the message in Settings, e.g.
`[28444] Developer console is not set up correctly` (the Android OAuth client or its SHA-1 is missing, or it's in a
different Google Cloud project) or the server's reason such as `Unacceptable audience in id_token` (the Web client ID
isn't in Supabase's Client IDs) or a nonce mismatch. Release builds show only the plain message. No message — debug
or release — ever contains a token, header or URL (`safeFailureDescription`).

Without step 4 the Settings section says connecting an account isn't available and offers no sign-in button.

## First end-to-end test (after setup)

Use a test Google account and test records only. Device A: add a wallet and a transaction → Settings → Connect with
Google → check the row in Supabase (Table editor → `transactions`, `user_id` = that account's id). Edit the note →
Sync now → note updated, still one row. Sync now twice more → still one row. Disconnect → confirm; the transaction leaves A (it is still in the account,
and comes back if A signs in again). Device B (or a clean install), same account → Connect → the wallet and
transaction arrive with the edited note. Sign in on B with a second test account → B’s local ledger is removed
(after a confirmation if anything on B has not synced) and nothing of account 1 is uploaded under account 2.

## Known limitations

- Device clocks still break ties between **genuinely concurrent** edits (both made from the same version before either
  synced). A device whose clock is far in the past can lose such a conflict it should have won; the edit is not kept
  as a recoverable copy. Sequential edits never depend on clocks. Keeping the losing version (e.g. a local conflict
  log the user can restore from) is the next step if this proves to matter in practice.
- A pull that applies a remote delete writes a local tombstone too; pushing it is harmless (the row is already
  deleted) but costs one extra request.
- A child row whose parent was deleted is kept by restoring that parent locally (see the pull step). The restored
  parent is not uploaded, so it does not undelete the account on a device that already removed it.
- Switching accounts wipes this phone's ledger first (see Sign-out). Unsynced changes are kept only if the user
  cancels the switch and signs back in to the original account.
- Preferences and goal photos are not synced.
- Rows with identical meaning created separately before their first sync are not de-duplicated (seed categories are
  the exception). Categories seeded by older versions (before v6) carry random ids, so two upgraded devices can show
  duplicate default income categories.
- Not exercised yet: real Google sign-in, a real push/pull against Supabase from the app (including PostgREST's
  handling of the keyset `or` filter and `return=representation` upserts, which compile against supabase-kt but have
  only been validated as the equivalent SQL), two real accounts, R8 release behaviour of sync at runtime. JVM tests run
  the engine against an in-memory server that mirrors the migrations (`FakeSyncServer`); the SQL-level checks run
  against the real database.
